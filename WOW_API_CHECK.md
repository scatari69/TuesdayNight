# Проверка WoW API

Дата: 22 октября 2026. Проверены публичные read-only запросы, без регистрации
приложений и без изменения данных. Retail. Контрольная гильдия: Echo, EU / Tarren
Mill; контрольные персонажи: Swagsurge и Justwait из её ответа `members`.
Это примеры для проверки контракта, не настройки будущего бота.

Обновление реализации: OAuth-привязка теперь добавлена через `/character link`
и `/character add`; ручное подтверждение офицером не реализовано. Инструкции
настройки ключей и HTTPS callback находятся в README. Живая авторизация Blizzard
по-прежнему не проверена: unit-тесты используют синтетические ответы.

## Результат живых запросов

Базовый адрес: `https://raider.io`. Все перечисленные ниже запросы дали HTTP 200
без API-ключа. Схемы сверены с [официальным Swagger](https://raider.io/swagger.json).

| Назначение | GET endpoint и параметры | Проверенные поля |
| --- | --- | --- |
| Гильдия, прогресс, ранг, состав | `/api/v1/guilds/profile?region=eu&realm=tarren-mill&name=Echo&fields=raid_progression,raid_rankings,members` | `raid_progression`, `raid_rankings`, `members[].character` |
| ilvl, рейтинг, опыт | `/api/v1/characters/profile?region=eu&realm=tarren-mill&name=Swagsurge&fields=gear,mythic_plus_scores_by_season:current,mythic_plus_best_runs:all,mythic_plus_recent_runs` | `gear.item_level_equipped`, сезонные `scores`, массивы прохождений |
| Персонаж без сезонных прохождений | Тот же endpoint с `name=Justwait` | Успешный профиль, нулевые сезонные scores и пустые массивы runs |
| Сезоны и подземелья | `/api/v1/mythic-plus/static-data?expansion_id=11` | `seasons`, `dungeons` |
| Рейды | `/api/v1/raiding/static-data?expansion_id=11` | `raids` |
| Детали прохождения | `/api/v1/mythic-plus/run-details?season=season-mn-2&id=21515104` | Уровень, время, `roster` с ролями |

Дополнительно локальные assert-проверки подтвердили структуру данных: непустой
состав и рейдовые данные; числовой equipped ilvl; четыре категории scores;
роль tank в записи забега и его специализации; успешное прохождение в таймер;
совпадение ID с run-details; состав последнего — один танк, один хил, три DPS.
Полные ответы оставлены только во временном `/tmp`, пользовательские данные
и списки игроков не добавлены в репозиторий.

Первый запрос к персонажу Gingi дал HTTP 400. После выбора персонажей из реально
вернувшегося состава оба запроса успешны. Не считать произвольное известное имя
существующим профилем и не превращать ошибку поиска в нулевой рейтинг.

## Что это меняет для проекта

**Для MVP достаточно одного провайдера — Raider.IO.** Blizzard можно подключить
позже для прямого состава/профилей и подтверждения владения. Обход списка
`members` и запрос профиля каждого персонажа нужны для гильдейских топов:
готового проверенного ответа «топ гильдии по ilvl и М+» в этой проверке нет.
В контрольной гильдии пришёл 951 участник — один полный проход означает примерно
952 запроса. Это число не включает дополнительные запросы деталей прохождений.
Делать проход постепенно и переиспользовать кэш, не запускать его по каждому клику.

Ранг проверен как `raid_rankings[raid_slug][difficulty].realm`, прогресс — отдельно.
В ответе несколько рейдов и составной tier, поэтому не выбирать первый ключ
объекта: явно задавать рейд/tier. Встречается rank 0 — это не «нулевое место»;
показывать отсутствие ранга, отдельно от HTTP-сбоя.

В контрольном профиле есть общий рейтинг и рейтинг танка, а также опыт timed +10
танком. Эти данные позволяют автоматически подтвердить соответствие минимальным
требованиям. Проверять общий рейтинг и рейтинг выбранной роли; опыт подземелья
проверять по записи, а не по текущей специализации.

Текущий сезон брать из ответа с `:current` и сопоставлять со справочником; номер
расширения и slug сезона выше — параметры проверки, не вечные константы бота.

## Ограничения и обязательные решения

1. **История неполная.** По [описанию параметров](https://raider.io/api), recent —
   последние десять, best — лучшие по очкам; `:all` снимает ограничение списка
   best, но не превращает его в полную историю. Высокий нетаймленный забег может
   скрывать более низкий timed; лучшая запись на DPS не покрывает весь опыт танка.
   Положительное свидетельство использовать для допуска; недостающий опыт
   направлять на проверку лидеру с причиной `Insufficient verified data`.
2. **Свежесть источника отдельно от нашего кэша.** В одном профиле дата получения
   данных персонажа была 21 октября, а `gear.updated_at` — 19 октября. В другом
   экипировка датировалась августом. Свежий HTTP 200 не доказывает свежесть ilvl.
   Сохранять `fetched_at`, `last_crawled_at` и дату gear, если она присутствует;
   отсутствующую дату не придумывать. Устаревший снимок не блокирует отображение
   с отметкой, но может требовать одобрения лидера для Push.
3. **Нет доказательства отсутствия опыта.** Нули и пустые runs описывают известные
   провайдеру данные, а не гарантированное отсутствие прохождений в игре.
4. **Квоты.** Официальная спецификация требует обработки 429 и `Retry-After`,
   описывает `X-RateLimit-*` и возможность ключа приложения для повышенных лимитов.
   В наших успешных ответах этих заголовков не было. Точную численную квоту не
   подтвердил; не закладывать предполагаемые 300 запросов/минуту. Ограничение
   нагрузки настраивать консервативно и не проверять квоту нагрузочным спамом.
5. **Атрибуция.** В дашборде и карточках с данными добавить ссылку на Raider.IO:
   это требование [условий API](https://raider.io/api).
6. **Роли в забеге доступны.** Для проверенного персонажа они уже присутствуют
   в best/recent. `run-details` годится для уточнения, но не нужен для каждого
   вступления. Роль персонажа в Discord-группе остаётся выбранной им ролью;
   бот не видит автоматически, на какой специализации он сейчас в игре.
7. **Ключ в сумке и фактический старт не проверены.** Уровень/подземелье будущего
   ключа вводит создатель; `Start` фиксирует состояние Discord-сбора. Публичные
   ответы, проверенные здесь, не подтверждают наличие этого ключа в инвентаре
   и не запускают подземелье. Desktop/live tracking для MVP не нужен.

## Blizzard: дополнительный, пока не проверенный с авторизацией

В окружении процесса нет `BLIZZARD_CLIENT_ID` / `BLIZZARD_CLIENT_SECRET` или
`BNET_CLIENT_ID` / `BNET_CLIENT_SECRET`. Секретные файлы не читались.
Прямой запрос roster без токена вернул HTTP 404; это **не доказательство**
отсутствия гильдии или неработоспособности авторизованного API.

Следующие запросы остаются кандидатами для интеграционной проверки с ключами
приложения; успешные ответы в этой сессии не получены:

| Данные | Endpoint | Namespace / доступ |
| --- | --- | --- |
| Токен приложения | `POST https://oauth.battle.net/token`, `grant_type=client_credentials` | Client ID + Client Secret; токен передавать через Bearer header |
| Состав | `GET /data/wow/guild/{realmSlug}/{guildSlug}/roster` | `profile-{region}` |
| Общая карточка, equipped ilvl | `GET /profile/wow/character/{realmSlug}/{characterName}` | `profile-{region}`; кандидат поля `equipped_item_level` |
| Предметы экипировки | `GET /profile/wow/character/{realmSlug}/{characterName}/equipment` | `profile-{region}`; для одного среднего ilvl полный список предметов не нужен |
| М+ профиль и сезон | `GET /profile/wow/character/{realmSlug}/{characterName}/mythic-keystone-profile` и `/season/{seasonId}` | `profile-{region}` |
| Сезоны/подземелья | `GET /data/wow/mythic-keystone/season/index` и `/season/{seasonId}` | `dynamic-{region}` |
| Специализации и роли | `GET /data/wow/playable-specialization/index` и `/{specId}` | `static-{region}` |
| Подтверждение владения | `GET /profile/user/wow` | Пользовательский OAuth Authorization Code, scope `wow.profile` |

Для запросов WoW база — `https://{region}.api.blizzard.com`; locale английский.
Namespace зависит от семейства ресурса, а не только от префикса `/data`.
[Profile API](https://develop.battle.net/documentation/world-of-warcraft/profile-apis)
и [Game Data API](https://develop.battle.net/documentation/world-of-warcraft/game-data-apis)
в браузерном инструменте не отдали читаемые схемы. Поэтому поля, квоты и полноту
истории Blizzard здесь не называем проверенными.

Возможность подтверждения аккаунта через пользовательский OAuth и `wow.profile`
описана в [официальном анонсе Blizzard](https://us.forums.blizzard.com/en/blizzard/t/world-of-warcraft-api-update-visions-of-nzoth/3461).
Для проверки нужны зарегистрированное приложение, callback и согласие пользователя;
одного client-credentials токена недостаточно. Реализован OAuth-поток;
подтверждение персонажа офицером пока не добавляли.

## Следующий шаг

Реализовать MVP на Raider.IO: гильдия → состав → кэшируемые профили → дашборд;
допуск М+ по общему/ролевому рейтингу и найденным timed-прохождениям. Отсутствие
полной истории решать заявкой лидеру. Blizzard не блокирует этот вариант.
Проверка выбранной пользователем гильдии и OAuth Blizzard остаётся отдельным
интеграционным этапом; Warcraft Logs и другие провайдеры для этих требований
не нужны.
