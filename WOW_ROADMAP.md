# План развития TuesdayNight для WoW

Статус: дашборд, Battle.net-привязка и сборы М+ реализованы; далее пилот.
Пользовательский интерфейс — английский.
Первая версия рассчитана на WoW Retail и одну WoW-гильдию на Discord-сервер.
Регион, realm и гильдия настраиваются отдельно для каждого сервера.
Classic требует отдельной проверки доступности данных и не входит в первую версию.

Публичные API проверены 22 октября 2026: [результаты и ограничения](WOW_API_CHECK.md).
Для MVP достаточно Raider.IO; авторизованные запросы Blizzard пока не проверены.

## 1. Данные и персонажи

- Источник MVP: [Raider.IO API](https://raider.io/api) для состава гильдии,
  экипировки, рейдового прогресса, ранга и сезонного М+ рейтинга/выборок прохождений.
  Нужные поля подтверждены публичными запросами. Blizzard — последующее дополнение
  для прямых профилей и OAuth. Перед включением проверить выбранную гильдию;
  точная численная квота Raider.IO не подтверждена, нужен backoff по `Retry-After`.
- Идентичность персонажа: регион + realm + имя, по возможности также ID Blizzard.
  Discord ID пользователя хранится отдельно. Не переиспользовать Steam `links`.
- Планируемые команды: `/wow setup`, `/character add`, `/character list`,
  `/character main`, `/character remove`. Несколько персонажей на пользователя,
  один основной. Вступление в группу всегда конкретным персонажем и ролью.
- Самостоятельный ввод имени не доказывает владение персонажем. Основной способ
  привязки — Battle.net OAuth с `wow.profile`, одноразовым `state` и выбором из
  персонажей аккаунта. Подтверждение офицером возможно как резервный вариант.
  Повторная привязка чужого подтверждённого персонажа запрещена.
- Роль Discord даёт право пользоваться гильдейскими функциями. Состав WoW-гильдии
  берётся из API, а не приравнивается к участникам роли. Храним привязки и временный
  API-кэш, но не второй вручную поддерживаемый список состава.

Готовность этапа: офицер настроил гильдию, подтвердил персонажа; другой сервер
не видит эти настройки и привязки. Steam-профили продолжают работать отдельно.

## 2. Дашборд внутри Discord

Реализованный дашборд — одно сообщение с embeds, которое бот редактирует и
пытается закрепить (без права закрепления это делает модератор вручную).
Отдельный сайт для MVP не нужен. Команды: `/dashboard setup` для офицера,
`/dashboard refresh` с ограничением частоты. Пример содержимого:

| Блок | Что показываем |
| --- | --- |
| Raid progression | Название текущего рейда, прогресс по сложностям, ранг на realm по каждой доступной сложности, ссылка на источник |
| Top item level | Топ-10 персонажей гильдии по equipped ilvl, класс, realm, время обновления |
| Top Mythic+ | Топ-10 персонажей гильдии по общему рейтингу текущего сезона, класс, ссылка на профиль |
| Data status | Время последнего успешного обновления и число загруженных/доступных персонажей |

Именно топ персонажей: альты могут занимать несколько мест. Топ уникальных людей
по основному персонажу — отдельное возможное расширение, иначе непривязанные
игроки незаметно пропадут из гильдейского рейтинга.

Ранг берём у провайдера с явно указанными областью и сложностью; не вычисляем его
из числа убитых боссов. Неполученный ранг — `Unavailable`, отсутствие рейтинга —
`Unranked`, не ноль. Для connected realms показываем область рейтинга провайдера.

Предлагаемое обновление: каждые 30 минут; состав гильдии раз в час. Перед каждым
обновлением используем кэш, ограничиваем параллельные запросы и учитываем квоты.
Таймауты, backoff для 429/5xx, без полного обхода гильдии при каждом клике.
Отдельно показываем свежесть источника: успешный запрос не обновляет старый
снимок экипировки. Добавляем ссылки на Raider.IO согласно условиям API.
При сбое сохраняем последний успешный результат с отметкой `Stale`; неполную
загрузку помечаем явно. При смене сезона старый рейтинг не участвует в новом топе.
Удалённое сообщение пересоздаётся с сохранением нового ID; ошибки прав видит офицер.

Готовность этапа: дашборд переживает перезапуск, не плодит сообщения, показывает
частичный сбой и не выдаёт старые данные за актуальные.

## 3. Набор групп М+

Минимальный сценарий:

1. `/mplus create dungeon:... level:... character:... role:... start:... mode:...`
   создаёт карточку. Создатель занимает своё место и также проходит проверку допуска.
   Время показываем через Discord timestamps, чтобы часовые пояса не путали участников.
2. Карточка показывает подземелье, ключ, время, требования, лидера и пять мест:
   один tank, один healer, три DPS. Кнопки `Join`, `Leave`, `Cancel`, `Start`.
3. `Join` предлагает подтверждённого персонажа и доступную ему роль; проверка
   требований выполняется сервером при каждом вступлении, включая кнопки после рестарта.
4. Подходящий игрок занимает свободное место. Подходящий игрок при заполненной
   роли попадает в очередь этой роли. Оставшееся место не занимает случайный DPS
   вместо танка. Один Discord-пользователь не занимает несколько мест альтами.
5. `Leave` освобождает место; первому подходящему игроку очереди предлагается
   подтвердить участие с таймаутом. `Start` фиксирует готовую пятёрку; `Cancel`
   закрывает запись. Ушедший лидер передаёт лидерство или отменяет сбор.

У каждой группы отдельные ID, голоса и очередь. Нынешние общие `votes` и `/clear`
для этого не подходят: несколько групп должны собираться одновременно.

### Допуск: минимальные требования без верхней границы

Гильдия задаёт правила для диапазонов ключей: минимальный общий и ролевой сезонный рейтинг,
минимальный equipped ilvl и опыт timed-прохождений на выбранной роли.
Рейтинг — общий индикатор; опыт по роли и подземелью защищает от записи
опытного DPS в незнакомый ему высокий ключ танком.

Для первого варианта опыт можно считать так: максимальный timed-ключ текущего
сезона на выбранной роли не ниже `уровень группы − допустимый шаг`; для высоких
ключей дополнительно timed-прохождение выбранного подземелья. Допустимый шаг,
граница высоких ключей и пороги рейтинга/ilvl задаются офицером после проверки
данных текущего сезона. Raider.IO возвращает роль и специализацию в best/recent,
но эти выборки не содержат всю историю. Если подходящий забег не найден,
заявка требует проверки лидера: отсутствие записи не доказывает отсутствие опыта.
Не подменять историю прохождений текущей специализацией персонажа.

Пример механики, не готовые сезонные пороги: при допустимом шаге 2 игрок с timed
+8 на этой роли может претендовать на +10, но не на +12; остальные требования
также обязательны. Игрок с +12 может идти в +5 — верхнего ограничения нет.
Низкий общий рейтинг блокирует автоматическую запись в высокий ключ даже при
одном удачном прохождении. Рейтинг основного персонажа не переносится на альта.

| Ситуация | Поведение |
| --- | --- |
| Все требования выполнены, место свободно | Записать |
| Все требования выполнены, роль занята | Очередь по роли |
| Не хватает рейтинга, ilvl или опыта | Объяснить конкретную причину; предложить заявку лидеру |
| Профиль не подтверждён, роль невозможна для класса | Отклонить, объяснить исправление |
| API недоступен или данные устарели | Не записывать автоматически; обновить или отправить на проверку |
| Персонаж опытнее требований | Разрешить |

Два режима: `Push` с требованиями гильдии и `Learning` с явно более мягкими
условиями. Пороги по диапазонам ключей настраивает офицер; лидер делает
явное индивидуальное одобрение заявки с отметкой в карточке. Одобрение не обходит
владение персонажем, состав 1/1/3 и запрет дубликатов. Так друзья и альты могут
играть вместе по осознанному решению, не обходя фильтр незаметно.

Проверка допуска и занятие места выполняются одной транзакцией `Store.edit`;
HTTP выполняется до неё, затем проверяются актуальные настройки и свежесть снимка.
При старте повторно проверяем состав и доступные данные; проблемные заявки
возвращаются на проверку. Одновременные клики не должны дать шестого участника.

Готовность этапа: тесты покрывают низкий/высокий рейтинг в обе стороны, смену
роли, альтов, сезон, устаревший API, конкурирующие клики, очередь, отмену,
права лидера и перезапуск с активными группами.

## 4. Порядок реализации

| Этап | Результат и проверка |
| --- | --- |
| 1. Английский интерфейс | Перевести текущие сообщения и описания; сохранить команды, state и persistent ID; обновить тесты |
| 2. Дашборд — реализован | Три блока, обновление одного сообщения, кэш/таймауты, ошибки и свежесть; unit-тесты на синтетических ответах API. Остался пилот на тестовом Discord-сервере |
| 3. Привязка — реализована | Battle.net OAuth, одноразовый state, выбор персонажей и основного через Discord, защита от повторной привязки; осталась интеграционная проверка с ключами и HTTPS callback |
| 4. Группы М+ — реализованы | Независимые сборы, 1/1/3, сезонные правила, допуск, очередь с подтверждением, одобрение лидером, закрытие; конкурентные unit-тесты. Нужна проверка на тестовом Discord-сервере |
| 5. Пилот | Отдельный Discord-сервер: права, кнопки после рестарта, API-сбои, подбор порогов; затем включение на основном сервере |

Сохраняем `Store.read`/`Store.edit`, атомарную запись и изоляцию серверов.
Для новых полей добавляем безопасные значения по умолчанию и тест загрузки старого
state; существующие привязки не удаляем. HTTP-сессии закрываются вместе с клиентом.
Ключи API — в окружении, не в state или репозитории. Общие ответы без пингов;
уведомления участников только явно разрешённым адресатам.

После MVP: рейдовый календарь с записью и резервом, напоминания о сборах,
отчёты посещаемости. Автоформирование команд, Warcraft Logs, рекрутинг, сайт,
собственные оценки навыка и перенос JSON в БД пока не требуются.

Перед WoW-этапом нужно выбрать регион/realm/гильдию, подтвердить Retail,
назначить офицеров и согласовать правила для Learning/Push. Точные сезонные
пороги согласовываются с офицерами; ограничения истории по ролям описаны в отчёте API.
